托管业务的难题

托管和 WaaS 服务商常见的问题

01

客户都要合规，却各自采购、各自对接

每家企业客户单独接一套 KYT，成本高、周期长，小客户往往干脆不做。

DART 怎么解决

  • 你统一接入一次，为旗下每个企业钱包的充提自动筛查
  • 下游客户开箱即有 KYA / KYT，不用各自采购

证据某钱包与托管基础设施服务商工作日每天筛查 1.7–1.8 万次。

02

不同客户，风险偏好不同

支付客户、交易平台、项目方对风险的容忍度完全不一样，一套规则满足不了所有人。

DART 怎么解决

  • 规则集按客户分开：复制内置规则集，按客户的口径配置阈值和规则
  • 筛查时传入对应客户的规则集，结果和快照按客户留存

证据内置规则集只读，自定义规则集独立保存，可以说明任意时点用的是哪套规则。

03

MPC 归集时，问题资金混进了主钱包

充值地址的资金归集到主钱包后，问题资金就和正常资金混在一起，很难再拆开。

DART 怎么解决

  • 归集前先筛：对充值交易做流入方向筛查，命中的地址暂停归集
  • 按时间顺序向上游追，只计算转出前已经到账的钱

证据MPC 托管归集与 KYT 接入有现成指南，接入时我们一起梳理流程。

常见问题

托管服务商常问的问题

能不能为每个下游客户单独配置规则？

能。复制内置规则集为每个客户配置一套，筛查时传入对应的规则集，结果和快照按客户分开留存。

归集流程里应该在哪一步筛查？

建议在充值到账、归集之前筛查资金来源，命中的地址暂停归集，交给客户处置，避免问题资金混进主钱包。接入时我们一起梳理流程。

存量地址怎么处理？

用 CSV 批量导入，一次性重新筛查存量地址，之后再切换到实时筛查。

量大会不会影响速度？

制裁筛查 1 秒内返回；同步调用直接给结果，大批量和深度追踪可以用异步模式，返回任务 ID 再查询，不阻塞充提。

控制台和 API 能一起用吗？

能。控制台、REST API、MCP 和 CSV 批量共用同一个账号、同一份额度和同一批快照。
